# Вычисляемый аудит: один результат для интерфейса и CLI

Задача #29 плана #24. `computeSceneAudit()` в `js/runtime/scene-audit.js`
не читает сохранённый `PASS` или числа из истории дизайна. Она использует общий
контракт материалов/объектов, реестр отрисовки и `auditBuilding()` из #28.

## Три разных источника

**Требования** `SCENE_REQUIREMENTS` фиксируют состав NPC-маркеров, габарит
крафтовой 46×36, 86 рабочих сундуков и два бассейна 20×16. Они независимы
от текущих массивов: удаление жителя, сундука или воды не меняет требование.
**Результат** содержит фактические количества, ошибки, предупреждения и проверенные
показатели. **Golden** `tools/fixtures/geometry.json` отдельно защищает всю принятую
геометрию/палитры/подписи/инженерию; в этом изменении его хеши не обновлялись.

Старые декларации сохранены в `D.designHistory`, не `D.validation`. Часть старых
регрессий всё ещё сравнивает исторические договорённости, но проверки буквального
`status: PASS` удалены. История не является входом вычисляемого аудита и не выводится
зелёными индикаторами. Подстановка нового `D.validation={status:'PASS'}` ничего не меняет.

## Результат и границы

`FAIL` означает ошибки проверенного объёма. `WARN` означает отсутствие найденных
ошибок при неполных предметных метаданных. `PASS` возможен только без ошибок и
предупреждений и не обещает точную симуляцию Terraria. Текущие 240 предметных
исключений #27 дают WARN, а не выдуманные предметы или общий зелёный PASS.

Количество объектов, жителей-маркеров, будущих жителей, сундуков, пилонов,
эффективных фоновых тайлов и открываемых дверей берётся из данных/геометрии.
Объём воды вычисляется из размеров; отдельно проверяются записанное `tiles`,
наличие нужного бассейна, его размеры и твёрдые блоки внутри воды.

Цены/счастье NPC, игровые биомы, заселение, действие механизмов и будущие
телепорты вынесены в отдельные разделы **целей** и **непроверенных условий**.
Они не получают зелёную отметку. Строительные правила относятся к проектной
модели креплений, а не к полному игровому движку; неизвестные предметы остаются
явными предупреждениями. Освещение продолжается в отдельной #31.

В браузере отчёт рассчитывается один раз при `populate()`, до готовности первого
кадра, затем хранится в `sceneAudit`. Перетаскивание, zoom, выбор и отрисовка
не запускают его повторно. Геометрические нарушения не прячут карту: интерфейс
остаётся доступным, но показывает FAIL. Некорректные входные спецификации
по-прежнему останавливаются предыдущими startup-проверками до рендера.

## Проверки

```sh
node tools/check-audit.cjs
node tools/audit-scene.cjs
node tools/audit-scene.cjs --json
python tools/check-browser.py
```

CLI возвращает 1 при FAIL любой сцены, 0 при PASS/WARN и явно печатает предупреждения.
Это не ослабляет отдельную строгую проверку конструкции `audit-building.cjs`.
Проверены 36 регрессий вычисления/UI и настоящий ненулевой код CLI на повреждённой
временной копии со старым сохранённым PASS. Мутации не меняют рабочие данные.

HTTP smoke расширен до **96 сценариев**: прежние 80 плюс 16 случаев повреждения
стен/предмета/жителя/воды с полноценным запуском. Во всех положительных и новых
аудитных случаях JSON браузера сравнивается с независимым Node-запуском той же
чистой функции. Отдельный счётчик в тесте доказывает отсутствие пересчёта на кадрах.
В режиме FAIL/WARN проверяется отсутствие общего зелёного badge. Сообщения и
условия проекта экранируются перед вставкой в DOM.
